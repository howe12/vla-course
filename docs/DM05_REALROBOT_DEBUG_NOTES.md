# DM0.5 实机部署调试记录 — 从「抓取失败」到「起始位姿根因」

> 日期：2026-09-23 ~ 2026-09-24
> 平台：LEO-Gemini 双臂机器人（NUC 控制器）+ 云端 L40 推理容器
> 配套代码：`codes/step7_gemini/dm05/`
> 前置文档：`docs/DM05_DEPLOYMENT_HANDOFF.md`（部署流程与 API 约定）

---

## 0. 一句话结论

实机抓取失败**不是**因为图像域差异、不是推理延迟、不是时间戳、也不是训练不够，
而是因为**部署时机器人的静止起始姿态落在训练分布之外（OOD）**：
训练数据里 `right_shoulder ≈ 89.4°`（`[85,90)` 占 61.44%），
而机器人断电静止位是 `104.7°`（训练数据里只占 0.07%）。
模型在 OOD 起始状态下把右臂驱动得乱走，进而形成训练数据中根本不存在的
「左臂已到抓取位 + 右臂仍在动」的组合，于是输出的动作方向是错的。

**修复方式：启动时先把 14 个关节全部归位到训练数据的初始位姿**再开始推理。

## 1. 系统结构

```
┌─────────────── NUC (192.168.100.x) ───────────────┐        ┌──── 云端 GPU 容器 ────┐
│  3× USB 相机 (video0=front, video4=left,          │  SSH   │  DM0.5 LoRA 推理服务  │
│              video2=right)                        │ 隧道   │  POST /v1/infer       │
│  motor_executor_live_dm05.py                      │ ─────► │  :7891                │
│    ├─ 读 14 关节状态 + 3 路图像                    │        │  chunk = 50 × 14      │
│    ├─ 组 HTTP 请求 (3× base64 JPEG + state)        │ ◄───── │                       │
│    ├─ 收 50 步动作序列                             │        └───────────────────────┘
│    ├─ 安全限位 / 限速 / 超时熔断                    │
│    └─ 逐步下发到 GeminiFollower (双臂串口)          │
└───────────────────────────────────────────────────┘
```

关键点：`/v1/infer` 是**无状态**接口，每轮请求都必须带上当前 `state`。
在 `action_mode=RELATIVE`（默认）下，模型输出的是**相对增量**，
服务端 `ActionAbsolute` 会做 `state + delta`（夹爪维度保持绝对值）。
**因此请求里传入的 `state` 直接参与最终动作的计算** —— 这是后面判断
「起始位姿错误 → 动作错误」的因果链基础。

## 3. 逐条排除的假设

诊断阶段逐项做了消融/对照实验，下面这些**都不是**原因：

| 假设 | 验证方式 | 结论 |
|---|---|---|
| 图像域差异（相机/光照/背景） | NUC 实拍图 vs 训练图、灰度图消融 | 影响 < 0.11°，**排除** |
| front 相机裁剪（只取下半） | 裁剪前后动作 MAE | 0.64–0.86°，**排除** |
| 开环 horizon 选得太长 | N=5 / N=50 对照 | **N=50 反而更好**，排除 |
| 动作被安全限位截断得太狠 | chunk 内部步进速度统计 | 平均 0.24°/步，仅 6.9% 超速，**排除** |
| 图像与推理的时间戳/流程错位 | 查 API 契约 | 请求体**根本没有时间戳字段**，无状态，**排除** |
| 训练不充分 | 训练域内 teacher-forcing 复现 | h=0 时 MAE 0.71°；R_grip MAE 0.45°；夹爪稳态预测 0.12–0.63° → **模型对训练分布拟合很好**，排除 |

> 关于夹爪语义曾有一次误判：一度以为训练数据里夹爪闭合对应负值
> （判据 `< -30`），据此判断「模型对夹爪有盲区」。实际核对 30/30 集后确认
> **闭合值是 `+8`，不是负值**。新数据的夹爪语义为：
> `-80` = 空夹爪完全闭合（占 0.1% 帧）、`+8` = 夹住物体、`+55~64` = 完全张开。
> 教训：判据必须从数据本身统计得出，不能靠先验假设。

## 4. 根因定位

### 4.1 起始位姿的分布外程度

对训练数据每一集的**首帧**做统计：

| 关节 | 训练首帧均值 | 训练分布 | 机器人静止位 | 静止位在训练中的占比 |
|---|---|---|---|---|
| `right_shoulder` | 89.4° | `[85,90)` 占 **61.44%** | **104.7°** | **0.07%（17 帧）** |
| 其他 13 个关节 | — | 集中 | 偏差 1–20° | 尚可 |

`104.7°` 落在训练分布的**极边缘**。更糟的是它不是「静默不动」——
模型在这个 OOD 状态下会主动驱动右臂。

### 4.2 因果链

```
right_shoulder = 104.7°（OOD）
        │
        ▼
模型输出错误的右臂动作 → 右臂摆幅 124.6°（训练里右臂基本不动）
        │
        ▼
形成「左臂已到抓取位 + 右臂却在移动」的组合
   → 该组合在训练数据中不存在（最近邻距离 53.6°）
        │
        ▼
模型对左臂也给出错误方向
   chunk 末步目标距抓取位 35.5°，而实际只到 14.2°
        │
        ▼
抓取落空
```

补充一个关键旁证：在**真正下降去抓取**的 16 集里，右臂几乎是锁死的：

| 关节 | 抓取时刻均值 ± 标准差 |
|---|---|
| `left_waist` | 56.3 ± 1.9 |
| `left_shoulder` | −35.7 ± 5.1 |
| `left_elbow` | 39.0 ± 5.6 |
| `left_forearm_roll` | −8.7 ± 2.8 |
| `left_wrist_flex` | −74.6 ± 3.1 |
| `left_wrist_roll` | 55.6 ± 2.4 |
| `left_gripper` | 16.0 ± 4.7 |
| **`right_shoulder`** | **88.9 ± 0.1** |
| **`right_elbow`** | **−87.6 ± 0.2** |

也就是说：**抓取全程是左臂单方面完成的，右臂必须保持不动**。
这解释了为什么右臂一旦在 OOD 下乱走，整个策略就崩了。

## 5. 修复：启动时整机归位到训练初始位姿

### 5.1 目标位姿

取 30 集首帧的**中位数**（单位：度），硬编码在
`motor_executor_live_dm05.py::TRAINING_INITIAL_POSE`：

| 关节 | 目标 | 关节 | 目标 |
|---|---|---|---|
| `left_waist` | 0.8 | `right_waist` | −2.1 |
| `left_shoulder` | 84.5 | `right_shoulder` | 89.0 |
| `left_elbow` | −89.7 | `right_elbow` | −87.6 |
| `left_forearm_roll` | −8.3 | `right_forearm_roll` | −5.2 |
| `left_wrist_flex` | −13.7 | `right_wrist_flex` | −17.2 |
| `left_wrist_roll` | 9.5 | `right_wrist_roll` | 5.5 |
| `left_gripper` | 15.2 | `right_gripper` | 15.7 |

用法：`--home-mode initial`（默认）。另有 `grip`（仅开夹爪）与 `off`。

### 5.2 归位效果（30 轮对照实测）

| 指标 | 归位前 | 归位后 | 变化 |
|---|---|---|---|
| `chunk[0]` 与当前 state 最大偏差 | 1.260° | 0.860° | **−32%** |
| 安全告警条数 | 3690 | 2872 | **−22%** |
| `right_shoulder` 摆幅 | 124.6° | 85.4° | **−31%** |
| `right_elbow` 摆幅 | 110.4° | 82.5° | **−25%** |
| 左臂到达 `left_shoulder` | 31.9° | −3.1°（目标 −35.7） | **+35°** |
| 左臂到达 `left_elbow` | −21.6° | 10.8°（目标 39.0） | **+32°** |
| 左臂到达 `left_wrist_roll` | 38.6° | 57.4°（目标 55.6） | **✓ 到位** |
| 7 维抓取位对齐距离 | 95.3° | 57.2° | **−40%** |

残余差距（`left_shoulder` 还差 32.6°、`left_elbow` 还差 28.2°、
`left_wrist_flex` 过冲 26.4°）说明**归位只解决了起始条件，策略本身仍有误差**，
但方向已经对了。

### 5.3 归位实现踩的两个坑

**坑 1：状态读取只有约 3 Hz。**

`SgrMotorsBus.read("Present_Position")` 返回的是 `deepcopy(self.current_positions)`
—— 后台线程的缓存，**不是实时串口轮询**。
最初写成「每 50ms 发一次 `cur + 1.5°`」的渐进式，在缓存未更新的窗口里会
反复重发同一个目标，实际推进极慢：**实测 40s 只走了 5.8°**。
改为「分段直发 + 等本段真正到位」后，10° 约 0.6s。

**坑 2：逐个关节串行 → 全局卡死。**

第一版对每个关节各自 `while` 循环归位（串行）。14 个关节逐个等，
总耗时爆炸；更致命的是只要有一个关节卡在容差边缘，其余关节**永远轮不到**：
**实测 90s 只让 4 个关节动了不到 3°**，最后输出「控制循环完成，共 0 步」。

改为**所有待归位关节同步推进**：每一段让所有未到位的关节各走 `step_deg`，
段数 = `max(偏差) / step_deg`，**与关节个数无关**。

同步改正后实测（`probe_home.py`，`step_deg=5.0`）：

```
归位前最大偏差 95.6°  →  归位后最大残余偏差 1.50°     19 段 / 22.8s
14 个关节全部在 ±1.5° 以内（✅）
```

另一个必须注意的点：**下发的 action 字典必须包含全部 14 个关节**。
只填部分关节时，未填的关节没有目标位置，会被驱动层当作 0 处理。

### 5.4 夹爪的机械行为

`disconnect()` 关闭扭矩后，**夹爪会弹回 `-80°`**（机械弹簧复位），
`right_shoulder` 也会回到约 98–104°。所以：

- 每次新进程启动时，看到的就是「夹爪 −80、右肩 ~98」的静止位；
- **归位必须在同一个已连接、扭矩使能的进程内完成**，不能跨进程。

## 6. 本轮修掉的其他问题

### 6.1 `motor_executor.py` 限位单位 bug（最隐蔽的一个）

`SafetyConfig.limits` 的输入单位是 **0.1 度**，但默认限位表写的是
`(-100, 100)` —— 被当成**度**在用。结果所有目标都被夹到 `±10°`，
并产生假的「变化量 740 超限」告警，机械臂永远朝 ±10° 爬。

自洽验证：`835 → clamp → 100`，`|100 − 840| = 740`，与日志中的 740 完全吻合。

已按 0.1 度单位重写：

| 关节 | `SAFE_LIMITS`（默认，训练范围 + ~4° 余量） | `LOOSE_LIMITS`（`--loose-limits`） |
|---|---|---|
| `waist` | (−600, 510) | (−700, 600) |
| `shoulder` | (−670, 1085) | (−800, 1200) |
| `elbow` | (−940, 755) | (−1000, 800) |
| `forearm_roll` | (−420, 200) | (−500, 300) |
| `wrist_flex` | (−1010, 220) | (−1100, 300) |
| `wrist_roll` | (−480, 660) | (−600, 700) |
| `gripper` | (−840, 705) | (−900, 800) |

### 6.2 相机左右接反

`CAMERA_MAP` 原为 `(0,"front"), (2,"left"), (4,"right")`，
实机上 `video2` / `video4` 是**反的**。修正为：

```python
CAMERA_MAP = [(0, "front"), (4, "left"), (2, "right")]
```

### 6.3 front 相机裁剪

只保留下半部分再缩放到 640×480（工作台在下半幅，上半幅是无效背景）。
裁剪后动作 MAE 0.64–0.86°，属可接受范围，且显著减小请求体。

### 6.4 两跳隧道导致的超时熔断

最初走「NUC → 本地机 → 云端」两跳 SSH 转发，推理延迟尖峰达 **14925 ms**，
超过执行器 10s 超时阈值 → 触发熔断，**60 个回合里有 12 个被整轮跳过**
（950/1500 步未执行）。

改为 **NUC 直连云端**（把 NUC 的 `id_rsa.pub` 加入云端 `authorized_keys`）后：

| 指标 | 两跳 | 直连 |
|---|---|---|
| 平均延迟 | 1439 ms | **836 ms** |
| 最大延迟 | 14925 ms | **1306 ms** |
| 熔断次数 | 550 次超时 | **0** |

### 6.5 云端 OpenDM 的 3 处补丁

在无 flash-attn 的容器里跑 DM0.5 需要打补丁（详见 `DM05_CLOUD_PATCH_BACKUP.md`）：

1. `dm05_arch.py::_real_init` — flash_attn 不可用时强制
   `config.vlm_config.vision_config._attn_implementation = "sdpa"`。
2. `dm05_arch.py::_resolve_vision_attn_implementation` — 不可用时**警告并返回
   `"sdpa"`**，而不是抛异常。
3. `trainer.py` — 两处 `self.accelerator.state.fsdp_plugin` 改为
   `getattr(self.accelerator.state, "fsdp_plugin", None)`。

另外必须设 `llm_attn_implementation="sdpa"` 和 `vision_attn_implementation="sdpa"`，
否则会触发 `InductorError: No valid triton configs ... flex_attention`。

## 7. 安全限速依据

ISO/TS 15066 协作机器人准静态接触限值：末端执行器 **0.25 m/s**。

`max_joint_delta` 单位是 **0.1 度/步**，`step_delay` 默认 50 ms：

| `--max-joint-delta` | 关节角速度 | 末端近似线速度 | 评价 |
|---|---|---|---|
| 5 | 15 °/s | ≈ 0.12 m/s | 调试推荐 |
| 10 | 30 °/s | ≈ 0.29 m/s | 略超 ISO |
| 15 | 45 °/s | ≈ 0.43 m/s | **超 ISO，不建议** |
| 20（默认） | 40 °/s | ≈ 0.38 m/s | 需评估 |

训练数据统计：手臂关节速度 95 分位约 **60–63 °/s**，
夹爪闭合速度中位数 **9.6 °/s** —— 也就是说默认的 40 °/s
**比夹爪在训练数据里的闭合速度还快 4 倍**。实机测试中实测峰值 14.0 °/s。

建议：调试期用 `--max-joint-delta 5`；确认稳定后再逐级放宽。

## 8. 用法速查

```bash
# NUC 上
cd ~/vla-dm05
export DM05_REMOTE_HOST=<推理服务主机>; export DM05_REMOTE_PORT=<ssh端口>
./tunnel_dm05.sh &                     # 建立隧道

# 只做归位、不推理（安全验证用）
~/.venv/bin/python probe_home.py 5.0

# 完整实机运行（默认会先整机归位）
~/.venv/bin/python motor_executor_live_dm05.py \
    --live --home-mode initial --rounds 30 \
    --max-joint-delta 5 --step-delay 0.05 \
    --max-delta0-warn 20 --flush-camera
```

常用参数：

| 参数 | 说明 |
|---|---|
| `--home-mode {initial,grip,off}` | 启动归位模式，默认 `initial` |
| `--max-joint-delta` | 单步最大变化量（0.1 度） |
| `--max-delta0-warn` | `chunk[0]` 与 state 偏差超过该值（度）时跳过本轮 |
| `--flush-camera` | 开相机后排空缓冲，取真正最新帧 |
| `--loose-limits` | 换用更宽的机械边界 |
| `--grip-open` | 启动时夹爪张开到该角度（度） |

> `probe_home.py` 是独立的归位探针：只连电机、只做归位、打印
> 「归位前 / 目标 / 归位后 / 残余」对照表后断开，不跑推理。
> 改完归位逻辑先用它验证，比直接跑整轮实机安全得多。

## 9. 尚未验证 / 下一步

1. **归位后抓取是否真的成功 —— 尚未拿到完整结论。**
   本轮实机跑到第 19 轮（每轮约 3.7s，模型延迟稳定在 240–245 ms）时，
   NUC **整体从网络消失**（ARP 解析失败、全段扫描无响应、到云端的 SSH 隧道断开），
   测试中断，现场需人工确认 NUC 状态后重跑。
2. 残余对齐误差（`left_shoulder` 32.6°、`left_elbow` 28.2°）需要通过
   增加训练步数或补充抓取阶段数据来进一步收敛。
3. `left_wrist_flex` 过冲（−101.0° vs 目标 −74.6°）需要复盘是否与
   `SAFE_LIMITS.wrist_flex` 下限（−101.0°）贴边有关。
4. 建议后续每次实机测试都保留 `live_run_*.log`，便于逐轮对比
   `[诊断] state/chunk0/delta0` 与 `[安全] 本轮行程/峰值速度`。
